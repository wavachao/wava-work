# 基于证据的进化

## 触发与范围
- 在交付前的轻量检查中，只采纳明确长期偏好、可复用失败或真实流程缺口；单次参数留项目，未证实推测留候选。无新证据则不维护、不生成复盘。
- 当前任务优先；维护不得无限拖延。只修改第一方规则与资源，第三方技能接入/升级按技能包模块执行，不以进化扩大权限。

## 维护流程
1. 检查最新源码、用户修改、实际可写位置与保存方式，确定最小受影响模块。缺少能力时保留脱敏候选并说明阻塞，不声称已生效。
2. 写明证据、现有问题、预期行为与回退条件。搜索已有规则，优先合并、替换或删除；不逐次向入口追加要求。
3. 先建立相关任务基线，再修改最少内容。选择受影响与相邻场景验证；复杂更新独立前向测试，只提供技能与真实任务，不泄露预期答案。
4. 比较成果质量、耗时/成本与返工；脚本通过只证明相应检查，不等于agent表现或审美改善。尚未执行的比较明确标记。
5. 按技能包模块完成版本、清单与保存检查。公开源码、平台技能和目标客户端分别核对；回归时revert或恢复稳定版本，保留历史。

## 记录与规模
- 只在实际维护时记录evals/evolution.jsonl：脱敏证据、影响模块、行为变化、实际验证、限制和回退基线；不保存原始对话、认证或项目机密。
- 入口目标小于100行，作为内部维护预算而非效果保证；详细规则按需加载。每次新增都检查重复与冲突，无依据不加规则。
- 技能靠agent实际执行维护，不是后台训练或跨设备同步服务。当前任务不能未经验证就依赖新规则。
